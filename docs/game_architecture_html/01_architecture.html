01 Architecture

アーキテクチャ選定

本ゲームは「大量の物を集める」「まとめて落とす」「敵ゲージや崩落へ連鎖する」構造を持つ。プロトタイプでは、物理演算の見た目と実装速度を両立しつつ、複数人が衝突せず作業できる構造を優先する。

採用アーキテクチャ

項目採用理由プロトタイプ上の制約
ゲームエンジンUnity + C#見下ろし3D、Prefab、Inspector調整、ScriptableObject、物理・UI・入力の統合が速い。個人検証シーンを作りやすい。エンジン依存をGameObject層に閉じ、Core層にはUnity参照を極力入れない。
設計思想Component + Data Driven + Event Drivenプレイヤー、物、敵、ステージギミックを部品化し、ScriptableObjectで差し替え可能にする。イベントの乱用で流れが追えなくならないよう、直接依存してよい範囲を定義する。
物理方式ハイブリッド物理収集中は軽量なバッファ、解放時はRigidbody演出に切り替えることで大量物体でも破綻しにくい。全物体を常時Rigidbodyでシミュレーションしない。
シーン管理Additive Scene + GameplayShellBoot、Gameplay、Stage、UI、Debugを分け、共有シーンの編集衝突を減らす。統合シーンは統合担当のみ編集。各担当は個人検証シーンで作業する。
データ管理ScriptableObject定義敵、収集物、レシピ、ゲージ、ステージ設定をデザイナーでも調整しやすい。ScriptableObjectに実行時状態を保存しない。
通信Interface + EventChannel担当者間の依存を減らし、統合時に差し替えやすい。同期的に結果が必要な処理はinterface、通知だけでよい処理はeventに分ける。
テスト方針検証シーン + Debug Overlay + PlayMode Smoke Testゲームフィール中心のため、完全自動テストより見える検証を優先する。最低限、起動・収集・解放・敵ダウンが壊れていないことは毎回確認する。
最重要判断。 本作のボトルネックは「大量物体の見た目」と「大量物体の処理負荷」である。したがって、収集中の物体は実体を全部持つのではなく、CollectionBuffer内のPayloadとして扱う。見た目は追従Visual、攻撃時だけPoolから物理オブジェクトを出す。

レイヤー構成

Unityプロジェクト内では、以下の層に分ける。依存方向は上から下ではなく、基本的に「Presentation / Gameplay / Infrastructure が Core と Data を参照する」形にする。

層責務Unity依存主な中身
Core汎用ロジック、イベント、状態機械、時間、interface。原則なし。必要最小限。IGameSystem、EventBus、StateMachine、Result、Timer、MathUtility。
Dataゲーム調整値、定義データ、レシピ、敵設定。ScriptableObjectのみ許可。CollectableDefinition、EnemyDefinition、StageDefinition、RecipeDefinition。
Gameplayゲームルールと挙動。プレイヤー、収集、解放、敵、ステージ。あり。PlayerController、CollectionSystem、EnemyAttackGauge、StageTiltController。
PresentationUI、VFX、SFX、Camera、フィードバック。あり。HudPresenter、GaugeView、CameraShaker、HitEffectPlayer。
InfrastructureSceneLoad、ObjectPool、入力ラッパー、サービス生成。あり。SceneFlowController、PoolService、InputReader、CompositionRoot。
DebugToolsプロトタイプ検証用。チート、メトリクス、可視化。あり。DebugOverlay、SpawnDebugPanel、PrototypeMetricsLogger。

大量物体への設計方針

状態表現処理内容理由
フィールド上軽量Prefab、Collider、必要に応じてRigidbody。近距離だけ検出。遠距離は静的配置でよい。ステージに物が溢れている見た目を確保する。
収集中Payloadデータ + 追従Visual。CollectionBuffer内で個数、属性、質量、価値、形状を管理する。何十〜何百個を常時物理で連れ回さないため。
解放中Pooled Rigidbody / Projectile。一定時間だけ物理挙動。命中後はプールへ戻す。落とした気持ちよさは見せつつ負荷を制御する。
雪崩中演出用Flow Object + 一部物理。StageAvalancheFlowが方向と量を制御する。完全物理に頼ると再現性・調整性が低い。

採用しない方針

非採用理由代替案
全収集物を常時Rigidbodyで保持物量が増えるほど処理負荷、接触バグ、暴れが増える。収集中はPayload化、解放時だけ物理。
最初から完全ローグライク生成コア体験の検証よりも工数が大きい。StageDefinition差し替えで擬似的に変化を作る。
全機能をManager単体に集約並列作業時に競合しやすく、責務が崩れる。System単位、Module単位で分割する。
UIからGameplayを直接操作依存が逆流し、調整やテストが難しくなる。UIはEventを購読し、DebugのみCommand経由で操作する。

拡張ポイント

  • 新しい収集物。 CollectableDefinitionを追加し、Prefabと属性を登録する。
  • 新しい合体。 FusionRecipeDefinitionを追加し、必要素材、生成Payload、発動条件を設定する。
  • 新しい敵。 EnemyDefinitionとEnemyController派生、またはEnemyBehaviorStrategyを差し替える。
  • 新しいステージ。 StageDefinition、StageScene、SpawnZone、DropZone、EnemySlotを追加する。
  • 新しいボスギミック。 IBossGimmickを実装し、BossStageControllerへ登録する。
  • 製品版移行。 AssetProvider、SaveService、SceneFlowを差し替える。Gameplay本体には影響させない。
